# PostgreSQL / Supabase

Esta migração recria a estrutura sem recuperar registros do MySQL removido.
O original `schema.sql` permanece intacto. O arquivo para revisão/importação é
`schema.postgresql.sql`; nenhum comando de importação é executado pelo backend.

## Configuração local

Edite o `.env` da raiz, que permanece ignorado pelo Git:

```dotenv
DB_HOST=seu-host-session-pooler.supabase.com
DB_PORT=5432
DB_NAME=postgres
DB_USER=postgres.seu_project_ref
DB_PASSWORD=
DB_SSL_CA_PATH=backend/certs/prod-ca-2021.crt
JWT_SECRET=
PORT=3000
NODE_ENV=development
```

Preencha senha e segredo JWT somente localmente. Preserve o segredo JWT existente
para manter tokens válidos. O backend continua usando bcrypt e JWT de 24 horas;
não utiliza Supabase Auth nem acesso direto do frontend ao banco.

TLS é obrigatório, com `rejectUnauthorized: true`, validação de hostname padrão
do Node e TLS mínimo 1.2. Com `DB_SSL_CA_PATH` vazio, usa as autoridades confiáveis
do Node. A conexão Supabase validada neste projeto exige uma CA adicional: baixe o certificado
do projeto no painel Supabase e configure seu caminho local nessa variável.
Caminhos relativos partem da raiz do repositório. Não use `backend/certs/ca.pem`
(histórico Aiven), nem desative a validação de certificado. O código não usa
`DATABASE_URL` nem opções `sslmode` capazes de substituir a configuração TLS.

## Instalação e execução

```powershell
cd backend
npm ci
npm test
npm start
```

`npm start` escuta em `PORT`; importar `server.js` não abre uma porta. A conexão é
preguiçosa: iniciar a API não comprova acesso ao banco. O teste explícito abaixo
faz somente `SELECT 1` e encerra o pool, mas depende de credenciais, rede e TLS:

```powershell
npm run test:connection
```

A conectividade real foi validada com `SELECT 1 AS conectado`, usando a CA oficial,
TLS 1.3 e verificação do certificado/hostname. A CA deve ser obtida do painel do
Supabase, mantida localmente e indicada por `DB_SSL_CA_PATH`.

## Esquema e compatibilidade

- IDs `INTEGER GENERATED BY DEFAULT AS IDENTITY`, mantendo IDs numéricos na API.
- Tipos receita/despesa restritos por `CHECK`, sem criar ENUM global.
- `DECIMAL(10,2)` e `DECIMAL(15,2)` preservados. O pg retorna decimais como strings,
  como o mysql2 padrão; os totais continuam calculados com `Number` no controller.
- `DATE` continua serializando como Date/ISO à meia-noite local, como no mysql2
  padrão. Mantenha o mesmo `TZ` do backend anterior para preservar o horário ISO.
- `criado_em` usa `TIMESTAMPTZ` para representar um instante; sessões usam UTC.
  Não existem registros antigos a converter.
- FKs e `ON DELETE CASCADE` preservados; categorias continuam sendo texto nas
  movimentações, sem relacionamento novo com a tabela de categorias.
- Dez categorias iniciais com `ON CONFLICT (nome, tipo) DO NOTHING`.
- RLS habilitado sem políticas públicas nas quatro tabelas para bloquear acesso
  das roles públicas do Data API numa instalação nova. A conexão `postgres` do
  backend ignora RLS; o isolamento continua sendo responsabilidade dos filtros
  `usuario_id` dos models. Não há políticas preexistentes analisadas remotamente.
- `IF NOT EXISTS` permite reaplicar a criação, mas não corrige tabelas incompatíveis
  que já existam. Revise o esquema remoto antes de uma importação autorizada.
- Comparações de e-mail no PostgreSQL são sensíveis a maiúsculas. O esquema antigo
  não declara collation; confirme o comportamento desejado antes de normalizar
  e-mails ou introduzir índice insensível a maiúsculas.

Os endpoints de usuários, login e transações permanecem com os mesmos caminhos,
status e formatos. A exceção de segurança solicitada é `GET /api/usuarios`, que
mantém a lista, mas não retorna `senha`. A consulta interna de login mantém o hash
para bcrypt. Erros de e-mail duplicado usam SQLSTATE `23505` e retornam HTTP 409.

Os três arquivos locais de cartões já eram não rastreados e foram excluídos da
seleção de publicação. O model/controller receberam adaptações locais anteriores,
mas o módulo tem validação parcial, somente criação/listagem e nenhuma rota montada
no servidor. Não é necessário publicá-lo para migrar os endpoints existentes.
A tabela `cartoes` permanece no esquema aprovado. Não há novo endpoint público.
O frontend Web, os dados locais em localStorage e o aplicativo Mobile não foram
alterados. Dados salvos apenas no dispositivo não são importados para PostgreSQL.

## Validação e limites

`npm test` usa `node:test`, HTTP local e um pool simulado para testar cadastro,
bcrypt, unicidade, login/JWT, validações, CRUD de receita/despesa, totais, respostas
404 e isolamento entre dois usuários. Verifica também o pool real do pg sem abrir
conexões: aliases, TLS, parser de datas/decimais, falhas de configuração e JWT
obrigatório. Confirma HTTP 404 para cartões e movimentação legada, sem depender dos
três arquivos locais incompletos de cartões.

O esquema foi importado em transação no Supabase com autorização. Foram conferidos
as quatro tabelas, 27 colunas, PKs, FKs, UNIQUEs, CHECKs, índices, RLS e dez categorias.
Testes reais pela API validaram cadastro/login, JWT, ausência de hashes nas respostas,
CRUD de receita/despesa, precisão decimal, datas, totais e isolamento entre dois
usuários temporários. Os registros de homologação foram removidos seletivamente e
a limpeza foi confirmada. Esses testes reais precedem a atualização de segurança
das dependências; nesta etapa posterior foram repetidos somente os testes locais,
sem modificar o Supabase.

Permanecem pendentes, mediante autorização quando houver escrita no banco:

1. Reaplicar o script para testar idempotência no PostgreSQL real.
2. Testar violações reais de UNIQUE/CHECK/FKs, cascatas e concorrência.
3. Repetir navegação e fluxos completos no Web e no aplicativo React Native/Expo.

Resultado local: cinco testes aprovados, sintaxe dos arquivos JavaScript do
backend aprovada, esquema MySQL original inalterado e `git diff --check` sem
erros de whitespace. `npm run build` da raiz passou após instalar as dependências
já declaradas, com aviso de bundle acima de 500 kB. Isso confirma a compilação do
Web, mas não substitui testes de navegação ou integração com um banco real.

Revisão de segurança de 09/11/2026: atualizações compatíveis, sem overrides,
mantiveram Express 4. O lockfile agora resolve Express 4.22.3, body-parser 1.20.9,
proxy-addr 2.0.8, qs 6.16.2 e brace-expansion 5.0.12. Os cinco testes locais e
a sintaxe de 22 arquivos JavaScript passaram após essa atualização.

`npm audit --omit=dev` do backend reportou zero vulnerabilidades. A auditoria
completa caiu de 13 para nove avisos moderados, todos em ferramentas de
desenvolvimento ligados a minimatch. As faixas declaradas pelos consumidores
ainda usam minimatch 10; a correção indicada exige versão 11.0.1 ou superior.
Não foi aplicado downgrade, override ou `npm audit fix --force`. Uma mudança
fora dessas faixas depende de autorização e testes específicos das ferramentas.

A atualização compatível das dependências de produção da raiz resolveu Axios
1.21.0, Express 5.3.0, body-parser 2.4.0, proxy-addr 2.0.8, follow-redirects 1.16.3,
form-data 4.0.6, react-router/react-router-dom 7.18.5 e qs 6.17.1 no lockfile.
O backend continua separado, usando Express 4.22.3. A última auditoria de produção
retornou zero vulnerabilidades tanto na raiz quanto no backend. A auditoria completa
da raiz ainda registra 13 avisos de desenvolvimento: um baixo, cinco moderados e
sete altos. Nenhum override foi aplicado.

## ESLint e pendências de publicação

A configuração antiga da raiz importava `typescript-eslint`, mas a dependência
estava declarada apenas no pacote do backend. O comentário indicava a intenção de
reconhecer `require`. Como o código do projeto é JavaScript/JSX, a correção usa o
suporte nativo do ESLint a `sourceType: 'commonjs'` e `globals.node` no backend,
globals Node nas configurações da raiz e regras React/browser somente em `src`.
Não foi necessário instalar pacotes ou alterar manifests e lockfiles para isso.
O `typescript-eslint` já declarado no backend foi preservado, sem remover ferramentas
de desenvolvimento nesta correção mínima.

`npm run lint` agora carrega e analisa o projeto, mas retorna dez erros de código:

- Variáveis de `catch` não utilizadas: duas em cartaoController, uma em
  loginController, quatro em transacaoController e uma em usuarioController.
- Binding `senha` não utilizado na desestruturação do teste de listagem de usuários.
- `react-refresh/only-export-components` no export de `useFinanceiro` em
  `src/context/FinanceContext.jsx` (linha 66).

Esses problemas não foram corrigidos automaticamente e nenhuma regra foi
desabilitada. Os cinco testes locais e o build Web continuam passando. A configuração
de lint foi corrigida, mas o lint completo ainda não é um check aprovado.
Dois dos dez erros locais estão no controller de cartões excluído da publicação;
os outros oito permanecem nos arquivos selecionados. A correção foi adiada
explicitamente para uma atividade separada.

As referências locais consultadas apontam `main` em c0c7c8b, `develop` em 0b80837
e a feature em 0b80837, com a migração ainda sem commit. A develop está dois commits
à frente de origin/develop, e a main está 55 à frente de origin/main, segundo as
referências locais; confirme novamente o remoto antes de qualquer publicação.

Após aprovação para preparar o índice, revisar e criar o commit da feature,
publique primeiro a base develop sincronizada (ou use um PR de sincronização
se a branch for protegida). Só então publique a feature e abra seu PR para develop.
Assim o PR da migração não carregará também os dois commits de sincronização.
Não rebaseie, force-pushe ou publique a main como parte dessa operação.

O `.gitignore` protege `backend/certs/` e arquivos `.key`, `.pem`, `.p12`, `.pfx`,
`.jks` e `.keystore`. Certificados físicos e backups foram preservados. O antigo
`backend/certs/ca.pem` já era rastreado e contém apenas certificado público;
as regras não o retiram automaticamente do índice. O certificado Supabase continua
somente local. As regras não substituem revisão do conteúdo antes de cada commit.
